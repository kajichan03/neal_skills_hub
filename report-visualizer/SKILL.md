# report-visualizer：文字报告 → 可视化 HTML

## 这个 skill 是什么

不是排版器，不是美化器。输入一份文字报告，输出一个让读者「一眼看见状态、问题和下一步」的可视化 HTML。

核心信念：**可视化的质量不取决于渲染，取决于理解。**先搞清楚这份东西是什么、给谁看、读者关心什么，可视化该做什么自然就推导出来了。所以本 skill 的重心在理解层；渲染层只有一套与文档类型无关的视觉语法。

## 铁律

1. **先理解后渲染**——理解卡不过三道质量关，不动手写 HTML。
2. **映射在信息关系层**——「条件 vs 实况 → 判定卡」，不是「交易日报 → 情景卡」。禁止按文档体裁建模板库；模板库会让 skill 退化成一个文档类型的专用工具。
3. **读者是总开关**——读者不关心的事，做得再漂亮也是噪声。拿不准就回去重答「读者」这一问。
4. **不重画数据图**——文档自带的图（如 K 线 PNG）只做 base64 内联与排版联动；绝不凭文本中的数字重新生成数据图表（失真即造假）。图缺失就给占位框 + 缺图声明，不编造。
5. **单文件自包含**——产物是一个 HTML 文件：样式内联、脚本内联、图片 base64，离线双击即开。

## 阶段一：理解层（五问）

对输入文档回答五问，答案写成「理解卡」：

1. **形制**——这是什么东西？论证 / 记录 / 计划 / 数据汇编 / 流程契约 / 混合？形制决定读者怎么用它。
2. **问题**——它在答什么问题、解决什么麻烦？topic 不是 question（「市场分析」是 topic，「明天该不该动手、动哪只、什么时候动手」才是 question）。问题找错，后面全错。
3. **读者**——谁读？读完要做什么决定或动作？最关心的三件事是什么？（自问：哪件事可视化错了，读者会受伤？）
4. **骨架**——内容的依赖结构：谁支撑谁、谁先谁后。**按依赖排，不按目录顺序排**；压成一行行可视关系（`A → B → C`、`旧: X → 新: Y`）。
5. **要害**——对照第 3 问，哪里是 delta / 异常 / 风险 / 决策点——最值得被一眼看见的地方。

### 理解卡格式

```
文档: <文件名/标题>
形制: <一句话>
问题: <一句话，问句形式>
读者: <谁> | 用途: <什么决定/动作> | 关心: ① ② ③
骨架: <依赖链，3-10 行箭头图>
要害: ① <delta/异常/风险/决策点> ② …
可视化决策: (阶段二填写)
```

### 三道质量关（不过关就重做，不许渲染）

- **替换测试**：把这段理解拿去描述另一份同类文档，还成立吗？成立 = 太泛，重写。
- **指纹测试**：理解卡里有没有这份文档独占的术语、数字、结构？0 个 = 你理解的是「这类文档」不是「这份」。
- **方向测试**：骨架有依赖方向吗？还是只是目录换皮？目录换皮 = 没读懂。

## 阶段二：可视化决策层

从理解卡推导，不查体裁模板。映射表（信息关系 → 视觉语法）：

| 信息关系 | 视觉语法 | 何时用 |
|---|---|---|
| 构成（部分/整体） | 饼/环 | 份额、概率分布 |
| 对比（多对象同维度） | 柱/条形 | 排名、量级比较 |
| 演化（时间序列） | 折线/时间轴 | 趋势、流程时点 |
| 依赖/流程（A 推导 B） | DAG/泳道 | 推理链、流水线、多角色并行合成 |
| 状态核验（条件 vs 实况） | 判定卡 | 逐条 ✓/✗、距阈值、触发与否 |
| 位置/参考系（谁在哪） | 坐标图/阶梯/标尺 | 支撑阻力、阵营定位、价位带 |
| 风险/缺口 | 高亮警示带 | 数据缺口、冲突、教训、待办 |

页面 = 若干视觉语法的组合；**布局顺序 = 读者关心的优先级**，最上者最先看到。

每个可视化决策要在理解卡里写明三要素：**哪个信息关系、为什么值得可视化（对应读者哪件关心）、给谁看**。写不出 = 这块不该可视化，保留文字。

## 验收标准（kanban 原则作为质量门）

产物必须全过：

1. **3 秒测试**——读者 3 秒能说出这份东西的核心状态/结论。
2. **问题跳出**——异常、缺口、冲突不用找，自己显眼（警示色、置顶、放大）。
3. **行动可见**——读者下一步该做什么，从页面读得出来。
4. **反馈可见**（仅当文档属于周期性系列）——与上一期的对照、命中记录、改进台账，占据固定版面。

任何一条不过 → 回阶段一查理解卡，不是调样式。

## 渲染规范

- 单文件自包含 HTML：`<style>` 内联、原生 ES6+ JS 内联、图片 base64；不依赖外部 CDN（离线可用）。
- 图表优先纯 HTML/CSS/SVG 手绘。
- 忠实原文：数字、条款一字不改；可视化只做重排与凸显，不做改写、不做摘要式省略关键限定词。
- 配色用语义化 CSS 变量；状态色克制——警示色只给真正的异常，全篇皆红等于没有红。
- 中文排版：`-apple-system, 'PingFang SC', sans-serif`；数字用 tabular-nums 类处理对齐。

## 工作流

1. 读原文（全文，不跳读）。
2. 写理解卡 → 过三道质量关 → 给用户确认（用户可改）。
3. 填「可视化决策」列（每条三要素）。
4. 渲染 HTML，输出到用户指定位置（默认与源文件同目录，文件名加 `-visual` 后缀）。
5. 过 kanban 验收四条；把理解卡摘要与产物路径一并交付给用户。

## Gotchas（AI 常见翻车点）

- *AI 默认按目录顺序排版*——目录换皮不是可视化。骨架必须有依赖方向。
- *AI 默认堆图表*——能画饼的地方都画饼。每块可视化先答三要素，答不出就留文字。
- *AI 默认「美化」数字*——四舍五入、约掉限定词。金融/合规类文档，数字与口径注一字不动。
- *AI 默认给缺失的图编造内容*——缺图就占位 + 声明，绝不用文本数字重画数据图。
- *AI 默认全篇高亮*——警示色泛滥 = 没有警示。只有「要害」配得上警示色。

## Worked example：每日交易研判报告

一份周期性交易研判日报跑通两阶段的完整记录——用来证明映射是**推导**出来的，不是写死的。

输入特征：昨日检验（5 情景逐腿核验）/ 今日复盘（多导师并行判定 + 查表推导 + 冲突裁决）/ 明日预判（5 情景赋权）/ 个股计划（买卖两表条款）/ 执行契约（T-0…T-6 全时段）。

理解卡摘要：

```
文档: 每日复盘与预判（周期性，每日一篇）
形制: 研判报告 + 执行契约，机器管线生成，混合体裁
问题: 昨天预判对了没有 → 今天市场是什么状态 → 明天该怎么办？
读者: 作者本人 | 用途: 盘前/盘中/盘后三时点的操作决策 | 关心: ① 今日姿态 ② 条款触发与逼近 ③ 数据缺口
骨架: 昨日预判 → 检验 → 教训沉淀 → 状态判定(三导师并行) → 查表推导 → 冲突裁决 → 方向结论 → 情景赋权 → 个股条款 → 执行契约 → (次日检验，闭环)
要害: ① 未落档日且三腿贴线 ② 破线票名单 ③ 顺延触发 ④ 缺口清单
```

推导出的可视化决策（注意：全部来自信息关系，无一条来自「这是交易日报」）：

| 内容块 | 信息关系 | 视觉语法 | 对应读者关心 |
|---|---|---|---|
| 情景概率分布 | 构成 | donut + 命中标注 | ① 今日姿态 |
| 昨日逐档核验 | 条件 vs 实况 | 判定卡：逐腿 ✓/✗ + 距阈值 | ① 今日姿态 |
| 复盘推理链 | 依赖/流程 | 三导师泳道 → 查表 → 裁决 → 结论 | （学习研判路径） |
| 个股买卖三线 | 位置/参考系 | 价位标尺 + 自带 K 线 base64 内联 | ② 条款触发与逼近 |
| 执行契约 | 演化/时间 | T-0…T-6 时间轴 | ③ 何时做什么 |
| 缺口与教训 | 风险 | 顶部警示带 + 改进台账 | ③ 数据缺口 |

换一份 PRD 进来：读者是评审者，要害是范围与未决冲突，推导出的页面完全不同——引擎不变。
