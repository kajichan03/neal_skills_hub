# Context Portal - 活的上下文系统

**Context Portal** 是一个产品 & 代码双轨上下文管理系统，建立产品规则与代码规则之间的桥梁，确保"应该是什么"与"实际是什么"保持一致。

## 核心能力

| 能力 | 说明 | 价值 |
|------|------|------|
| **产品规则建立** | 从 PRD 提取功能、规则、用户故事 | 建立产品规则基准 |
| **产品规则更新** | 基于新 PRD 增量更新上下文 | 维护规则基准最新状态 |
| **代码规则提取** | 从代码提取隐式业务规则 | 发现代码实现的真实逻辑 |
| **一致性检查** | 比对代码规则 vs 产品规则 | 防止代码违背产品意图 |
| **产品影响分析** | 代码变更影响哪些产品功能 | 评估变更范围，降低风险 |

## When to Use

- ✅ 需要初始化产品上下文数据库（已有历史 PRD）
- ✅ 完成产品设计后需要更新产品上下文
- ✅ 需要从代码仓库提取业务规则
- ✅ 提交代码前检查是否与产品规则冲突
- ✅ 评估代码变更的产品影响范围
- ✅ 查询产品功能的状态、规则、权限定义
- ✅ 发现产品文档中缺失的业务规则

## When NOT to Use

- ❌ 仅需简单的文件读写操作
- ❌ 临时性的文档查看，无需建立上下文数据库
- ❌ 代码编译、测试等技术操作

## 智能合并组件 (Intelligent Merge)

Context Portal 的核心能力之一是**智能文档合并** - 能将变更内容合并到基础文档的正确位置，而非简单追加。

### 组件架构

```
变更文档                    基础文档
   │                          │
   ▼                          ▼
┌─────────────────┐    ┌─────────────────┐
│ content_        │    │ document_       │
│ extractor.py    │    │ parser.py       │
│                 │    │                 │
│ - 提取标题结构  │    │ - 解析Markdown  │
│ - 识别表格      │    │ - 构建标题树    │
│ - 分析变更意图  │    │ - 定位模块位置  │
└────────┬────────┘    └────────┬────────┘
         │                      │
         └──────────┬───────────┘
                    ▼
         ┌─────────────────────┐
         │  document_merger.py │
         │                     │
         │  合并策略引擎        │
         │  - INSERT_UNDER     │
         │  - APPEND (fallback)│
         └──────────┬──────────┘
                    ▼
           合并后的文档
```

### 核心模块

| 模块 | 文件 | 职责 |
|------|------|------|
| 文档解析器 | `scripts/document_parser.py` | 解析Markdown层级结构，构建标题树 |
| 内容提取器 | `scripts/content_extractor.py` | 提取变更文档的结构化内容 |
| 文档合并器 | `scripts/document_merger.py` | 智能合并内容到正确位置 |

### 合并策略

#### INSERT_UNDER（首选策略）

将变更内容插入到指定模块的对应章节下。

**适用场景**:
- 字段定义更新 → 插入到对应工单的"工单字段"章节
- 业务规则补充 → 插入到对应功能的"业务规则"章节
- 状态定义变更 → 插入到对应功能的"状态定义"章节

**定位逻辑**:
1. 从变更文档标题提取目标模块关键词（泳道/工单/变更等）
2. 在基础文档中查找对应模块路径
3. 查找目标章节（字段/规则/状态）
4. 确定插入位置（章节末尾或同级标题后）

#### APPEND（回退策略）

仅在无法定位目标模块时，将内容追加到文档末尾。

#### 增强指令 1: 字段传播（Field Propagation）

当变更文档涉及字段重命名或删除时，必须在**所有相关位置**同步修改：

1. 识别变更字段的名称（旧名称 → 新名称）
2. 扫描基础文档中该字段的所有出现位置
3. 在所有相关工单类型/页面中同步应用相同变更
4. 在 `conflict-report.md` 的"变更摘要"中列出所有传播位置

**示例**：
- 变更：`MQ变更` → `泳道中间件`
- 传播位置：
  - 工单类型：泳道新建 → 详情区域字段
  - 工单类型：泳道变更 → 详情区域字段
  - 工单类型：泳道注销 → 详情区域字段
  - 泳道管理 → 泳道详情页 → 中间件信息

#### 增强指令 2: 表格结构升级（Table Structure Upgrade）

当表格增加、删除或重命名列时，同名/同类表格必须统一升级：

1. 识别变更表格的列结构变化（新增列/删除列/重命名列）
2. 在基础文档中查找所有同名或同类的表格
3. 统一应用列结构变更
4. 保留已有数据行的内容不变，仅调整表头

**示例**：
- 变更：中间件信息表格新增 `类型` 列
- 升级范围：泳道新建/变更/注销工单中的中间件表格、泳道详情页中的中间件表格

#### 增强指令 3: 信息架构图同步（Information Architecture Sync）

当页面结构发生增删改时，必须同步更新 `## 1. 信息架构图`：

1. 分析变更对页面/模块结构的影响（新增页面、删除字段区块、重命名模块）
2. 在信息架构图的树状结构中找到对应节点
3. 应用相同变更：
   - 新增页面 → 在对应父节点下新增分支
   - 删除字段/区块 → 从树中移除对应叶子节点
   - 重命名 → 同步修改节点名称
4. 保持树的层级关系和缩进格式与原文一致

**示例**：
- 变更：泳道详情页中间件信息拆分为 `泳道中间件` + `相关的基线中间件`
- 同步更新信息架构图中 `泳道详情页` 下的 `中间件信息` 节点

### 使用示例

```python
from scripts.document_merger import merge_documents

# 读取文档
with open('product-context.md', 'r') as f:
    base_content = f.read()

with open('lane-fields-update.md', 'r') as f:
    change_content = f.read()

# 执行智能合并
result = merge_documents(base_content, change_content)

# 保存结果
with open('product-context-updated.md', 'w') as f:
    f.write(result)
```

## Four Core Processes

### 流程 1: 产品上下文冷启动

**触发命令**: `/product-context:init`

**场景**: 已有历史 PRD/设计文档，需要初始化产品上下文数据库

**输入**: PRD 文档目录或文件列表

**处理流程**:
```
输入：PRD 文档目录/文件列表
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 0: PRD 发现与排序（PRD Discovery）                   │
│ 1. 扫描目录，发现所有 PRD 文件                            │
│ 2. 提取时间信息，按时间排序                               │
│ 3. 验证 PRD 完整性                                       │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1: 顺序处理 PRD（Sequential Processing）            │
│ PRD #1 (最早) ──► Extract ──► Index ──► Export          │
│ PRD #2 ─────────► Extract ──► Merge ──► Export          │
│ PRD #3 (最新) ──► Extract ──► Merge ──► Export          │
└─────────────────────────────────────────────────────────┘
           │
           ▼
输出：product-context-YYYY-MM-DD.md + context.db
```

**提取内容**:
| 内容类型 | 来源章节 | 存储为 Entity |
|---------|---------|--------------|
| 功能模块 | PRD 功能需求 | domain='product', type='module' |
| 用户场景 | PRD 目标用户 | domain='product', type='persona' |
| 页面结构 | PRD 页面结构 | domain='product', type='page' |
| 业务规则 | PRD 功能点下的规则表格 | domain='product', type='rule' |
| 状态定义 | PRD 状态定义表格 | domain='product', type='state' |
| 权限规则 | PRD 权限规则表格 | domain='product', type='permission' |

### 流程 2: 产品上下文更新

**触发命令**: `/product-context:update`

**场景**: 已有产品上下文数据库，基于新的 PRD/变更文档更新

**输入**: 
- 现有产品上下文文档 (product-context.md)
- 新 PRD/变更文档

**处理流程**:
```
输入：现有 product-context.md + 新 PRD/变更文档
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 0: 前置检查清单（Pre-flight Check）                 │
│ 1. 数据库存在性检查                                      │
│    - 检查 context.db 是否存在                          │
│    - 若不存在，提示用户是否需要初始化数据库                │
│      "检测到仅有 .md 文档，未找到 context.db。            │
│       是否需要初始化产品上下文数据库？                    │
│       [是] → 执行 /product-context:init                   │
│       [否] → 继续仅更新 .md 文档"                        │
│ 2. 字段传播扫描                                          │
│    - 扫描基础文档，识别变更文档中涉及的字段/表格          │
│    - 标记这些字段/表格在文档中的所有出现位置              │
│    - 为后续同步修改做准备                                │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1: 文档解析（Document Parsing）                     │
│ 使用 document_parser.py 解析基础文档结构：               │
│ - 构建标题层级树（Heading Tree）                        │
│ - 识别模块位置（工单中心、泳道管理等）                  │
│ - 定位章节边界（功能描述、业务规则、状态定义）          │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 2: 内容提取（Content Extraction）                   │
│ 使用 content_extractor.py 从变更文档提取：              │
│ - 标题结构（内容类型、目标位置）                        │
│ - 表格数据（字段定义、规则表格）                        │
│ - 分析变更意图（字段更新、规则变更）                    │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 3: 智能合并（Intelligent Merge）                    │
│ 使用 document_merger.py 执行智能合并：                  │
│                                                         │
│ 合并策略：                                               │
│ - INSERT_UNDER → 插入到指定模块的对应章节下             │
│   例：字段定义插入到 "泳道新建 > 工单字段"              │
│                                                         │
│ - APPEND → 仅在无法定位时追加到文档末尾（回退）         │
│                                                         │
│ 定位逻辑：                                               │
│ 1. 从变更文档标题提取目标模块（泳道/工单/变更等）       │
│ 2. 在基础文档中查找对应模块路径                         │
│ 3. 查找目标章节（字段/规则/状态）                       │
│ 4. 确定插入位置（章节末尾或同级标题后）                 │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 4: 冲突检测（Conflict Detection）                   │
│ - 同名章节内容对比                                       │
│ - 规则冲突标记                                           │
│ - 标记潜在冲突项，供 Step 5 统一输出                     │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 5: 后置校验与强制输出（Post-validation）            │
│                                                         │
│ 1. 信息架构图一致性校验                                  │
│    - 检查 `## 1. 信息架构图` 中的模块是否与 `## 2. 功能模块` │
│      的目录结构一致                                      │
│    - 发现遗漏或不匹配时自动修正                          │
│                                                         │
│ 2. 版本号与日期校验                                      │
│    - 确认文档头部的版本号和日期已正确更新                │
│                                                         │
│ 3. 强制输出 `conflict-report.md`                         │
│    - 无论是否存在冲突，都必须生成 `conflict-report.md`    │
│    - 报告结构：                                          │
│      * 检查范围                                          │
│      * 变更摘要（列出所有修改位置）                      │
│      * 检查结果（✅ 无冲突 / ⚠️ 规则冲突）                │
│      * 待确认项（至少列出 1-3 项，可写"无"）            │
│                                                         │
│ 4. 可选输出 `execution-report.md`                        │
│    - 记录完整执行流程、合并策略、优化建议                │
└─────────────────────────────────────────────────────────┘
           │
           ▼
输出：
- `product-context-YYYY-MM-DD.md`（更新的产品上下文文档）
- `context.db`（更新的数据库）
- `conflict-report.md`（**必须输出**，一致性检查报告）
- `execution-report.md`（可选，执行报告）
```

### 流程 3: 代码规则提取

**触发命令**: `/code-context:init` 或 `/code-context:update`

**场景**: 已有代码仓库，提取业务规则并与产品规则建立映射

**输入**: 代码仓库路径

**处理流程**:
```
输入：代码仓库路径
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 0: 代码扫描（Discovery）                            │
│ 扫描目标（按优先级）：                                    │
│ 1. 领域层（Domain Layer）- Entity/Model、状态机定义    │
│ 2. 应用层（Application Layer）- Service、权限注解      │
│ 3. 接口层（Interface Layer）- Controller、参数校验     │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1: 业务规则提取（Rule Extraction）                  │
│ 从代码中提取：                                           │
│ - 权限规则（@PreAuthorize, if (hasRole)）              │
│ - 状态规则（状态机、状态转换）                           │
│ - 前置条件（if (condition) throw）                     │
│ - 后置条件（字段赋值、状态变更）                         │
│ - 数据校验（@Valid, validation）                       │
│ - 业务约束（计数、限流）                                 │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 2: 规则匹配与映射                                   │
│ 如果已有产品上下文数据库：                                │
│ - 匹配代码规则与产品规则                                 │
│ - 建立 validates / implements 关系                     │
│ - 标记 orphan（孤儿规则，无产品文档）                   │
└─────────────────────────────────────────────────────────┘
           │
           ▼
输出：code-rules-YYYY-MM-DD.md
      rule-mapping-report.md
      orphaned-rules.md（需要补全到产品文档的规则）
```

**提取的规则类型**:
| 规则类型 | 代码特征 | 示例 |
|---------|---------|------|
| 权限规则 | @PreAuthorize, if (hasRole) | 只有审批人能审批 |
| 状态规则 | 状态机、状态转换 | 待审批→已审批→已完成 |
| 前置条件 | if (condition) throw | 只有待处理状态才能审批 |
| 后置条件 | 字段赋值、状态变更 | 审批后更新审批人字段 |
| 数据校验 | @Valid, validation | 订单金额必须大于 0 |
| 流程规则 | 方法调用顺序 | 先扣库存再创建订单 |
| 业务约束 | 计数、限流 | 每人每天最多申请 3 次 |

### 流程 4: 一致性检查与影响分析

**触发命令**: `/context:check-consistency`

**场景**: 代码变更时，检查与产品规则的一致性

**输入**: 
- 已有产品上下文数据库
- 代码规则映射
- 新代码变更（commit/PR）

**处理流程**:
```
输入：已有上下文 + 代码规则映射 + 新代码变更
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 0: 变更规则提取（Changed Rule Extraction）          │
│ - 获取 commit/PR 的变更文件列表                         │
│ - 提取：修改前规则（Old Rule）vs 修改后规则（New Rule） │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1: 一致性检查（Consistency Check）                  │
│ 检查场景：                                               │
│ 1. 规则冲突（明确冲突）- 角色/条件不一致                 │
│ 2. 规则弱化（可能的风险）- 删除了校验                    │
│ 3. 规则增强（正常）- 添加了额外约束                      │
└─────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────┐
│ Step 2: 产品影响分析（Product Impact Analysis）          │
│ 分析维度：                                               │
│ - 功能影响（直接影响、间接影响）                         │
│ - 用户场景影响（影响哪些角色）                           │
│ - 依赖功能影响（下游功能）                               │
│ - 测试覆盖建议                                           │
└─────────────────────────────────────────────────────────┘
           │
           ▼
输出：consistency-check-report.md
      impact-analysis-report.md
```

## Data Model

### Entity 表结构

```sql
CREATE TABLE entities (
    id TEXT PRIMARY KEY,              -- 实体唯一标识
    name TEXT NOT NULL,               -- 实体名称
    domain TEXT NOT NULL,             -- 领域：product | code
    type TEXT NOT NULL,               -- 类型：module|feature|rule|persona|page|service|api|model
    content TEXT NOT NULL,            -- 完整内容（Markdown）
    content_hash TEXT,                -- 内容哈希（用于快速比对）
    token_count INTEGER,              -- Token 数
    source_file TEXT,                 -- 来源文件
    source_type TEXT,                 -- 来源类型：prd | openapi | config | commit
    iteration_id TEXT,                -- 迭代标识
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Relation 表结构

```sql
CREATE TABLE relations (
    id TEXT PRIMARY KEY,
    from_entity TEXT NOT NULL,        -- 源实体 ID
    from_domain TEXT NOT NULL,        -- 源领域
    to_entity TEXT NOT NULL,          -- 目标实体 ID
    to_domain TEXT NOT NULL,          -- 目标领域
    relation_type TEXT NOT NULL,      -- 关系类型：implements | validates | conflicts | orphan
    iteration_id TEXT,
    confidence REAL DEFAULT 1.0,      -- 置信度
    is_cross_domain BOOLEAN,          -- 是否跨域
    metadata JSON,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## 双轨制：完整文档 + 结构化数据

为了同时满足**产品经理阅读**和**代码一致性检查**的需求，Context Portal 采用**双轨制**存储：

### 文件说明

| 文件 | 用途 | 适用场景 |
|------|------|----------|
| `product-context-full.md` | **完整文档**（原始文件拷贝） | 产品经理阅读、下一轮设计输入、查看详细说明 |
| `product-context-summary.md` | **摘要文档**（结构化生成） | 快速概览、目录导航 |
| `context.db` | **结构化数据库**（SQLite） | 代码一致性检查、规则检索、影响分析 |

### 使用指南

#### 场景 1：产品经理需要查看完整信息
```bash
# 直接阅读完整文档
open product-context-full.md

# 包含所有细节：
# - 审批流程表格（5个节点完整定义）
# - 表单字段属性（类型、必填、校验规则）
# - 泳道范围 Section 层级结构
# - 组件变更信息表格定义
# - 邮件通知模板完整内容
# - 流程日志节点显示规则
```

#### 场景 2：需要进行代码一致性检查
```bash
# 查询结构化数据库
python scripts/db_manager.py --db context.db --search "审批权限"

# 检查规则冲突
python scripts/db_manager.py --db context.db --conflicts

# 分析影响范围
/context:analyze-impact --entity "工单中心"
```

#### 场景 3：快速查看产品概览
```bash
# 阅读摘要文档
open product-context-summary.md

# 包含：
# - 功能模块列表
# - 用户角色汇总
# - 业务规则清单
# - 状态定义表
```

### 数据同步说明

- **完整文档**：原始文件的完整拷贝，保留所有叙述性内容
- **数据库**：从完整文档提取的结构化数据，用于机器查询
- **摘要文档**：从数据库生成的概览，用于快速了解

**重要**：完整文档是"主副本"，数据库是"索引副本"。如有更新，先修改完整文档，再重新导入数据库。

## Workflow Guidelines

### 原则 1: 产品规则是基准

- PRD 中的业务规则是权威定义（"应该是什么"）
- 代码规则是映射（"实际是什么"）
- 一致性检查确保两者一致

### 原则 2: 渐进式建立

1. **冷启动**: 从历史 PRD 建立产品规则基准
2. **增量更新**: 每次迭代更新产品规则
3. **代码映射**: 从代码提取规则，建立映射
4. **持续检查**: 提交前自动检查一致性

### 原则 3: 可追溯性

- 每个规则都有来源（PRD 文件、代码位置）
- 每次变更都有迭代标识
- 支持版本追溯和影响分析

### 原则 4: 结构一致性

- 页面结构变更必须同步反映到信息架构图
- 字段重命名/删除必须传播到所有相关工单类型和页面
- 表格结构升级必须统一应用到所有同名/同类表格
- 产品上下文文档的目录、信息架构图、功能模块章节三者必须保持一致

## Troubleshooting

| 问题 | 解决方案 |
|------|----------|
| PRD 文件格式不规范 | 尝试识别关键章节，提取可用信息，标注待确认项 |
| 代码规则提取不完整 | 检查是否扫描了正确的目录，手动指定业务逻辑文件 |
| 规则匹配失败 | 检查命名一致性，手动建立映射关系 |
| 一致性检查误报 | 检查规则定义是否过于严格，调整匹配逻辑 |
| context.db 损坏 | 从 PRD 重新冷启动，或从备份恢复 |
| 信息架构图未同步更新 | 检查智能合并阶段是否触发了架构图同步指令，手动补全遗漏节点 |
| 只有 .md 没有 context.db | 调用 `/product-context:init` 从现有 PRD 初始化数据库 |
